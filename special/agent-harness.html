What makes an agent?

The model may generate the next token. The harness decides what happens next in the world.

A source-grounded retelling of Rubric Labs’ “What is an Agent Harness?” · August 11, 2026

ModelPredicts, reasons, writes
+
HarnessLoops, remembers, acts, checks

An LLM becomes agentic when software wraps it in a running system. That system feeds the model context, interprets its tool calls, executes actions, decides what requires permission, and keeps the work moving until there is a result. In shorthand: Agent = Model + Harness.

1. The loop is the first ingredient

Even a chatbot needs a harness: something must collect a request, call the model, and return the answer. Agent harnesses extend that simple exchange into a reason–act loop.

The model can search, edit a file, run a command, inspect the result, and decide whether another step is needed. Modern harnesses make this loop durable enough for long tasks—and structured enough to delegate pieces of work.

2. Context is the agent’s working world

At every turn, the harness chooses what the model can see: its role, current facts, available tools, earlier messages, tool outputs, and the user’s latest request. That selection is not plumbing; it is part of the agent’s behavior.

Compaction: staying inside one run

Long loops eventually fill the context window. Compaction asks a model to summarize older material and removes the original detail from the active window. Done well, this keeps a long-running agent coherent instead of forcing it to stop at the context limit.

Memory: carrying useful knowledge forward

Compaction is temporary. Memory persists across runs. Harnesses commonly separate reusable procedural knowledge—often encoded as skills—from other experience and tacit judgment stored in memory files. The open problem is deciding what should be remembered, when it should be trusted, and how it should be corrected.

A good harness does not merely give a model more context. It gives the model the right context at the right moment.

3. Orchestration turns effort into a system

Planning

As agents take on larger tasks, the human has fewer opportunities to steer every step. A detailed plan and a visible todo list become an external working memory: they preserve the goal while implementation becomes more autonomous.

Dispatch

For complex tasks, a primary agent can delegate independent work to sub-agents and combine their results. This gives an agent elastic capacity, but it creates a coordination problem: fragmented state can lead to conflicting edits, duplicated work, or agents that lose sight of the main objective. Parallelism helps only when the harness also supplies boundaries and review.

4. Tools are where language meets reality

A typical tool has an input schema and an output schema. The model emits structured data; the harness validates it, runs the corresponding operation, waits for the result, and places that result back into context.

This is also where architecture becomes authorization. Should an agent control a signed-in browser, or should it use narrowly scoped APIs for reading, drafting, and sending? The tool interface determines not only what the agent can do, but how safely those actions can be governed.

Protocols such as MCP reduce repeated integration work by giving tools a shared interface. CLIs and clear documentation can serve a similar role; the important idea is that the harness needs a reliable bridge from model output to real capability.

5. Verification is part of agency

When an agent changes more of the world, “the model said it worked” is not enough. Harnesses can require unit tests, smoke tests, browser checks, or a reviewer sub-agent before returning a result.

Each method has limits. Tests written by the same agent may confirm its assumptions without proving the feature works for a user. Smoke tests reveal unknown unknowns, but the agent must know what to exercise. The direction of travel is toward training models in environments where checking their work is learned behavior rather than an afterthought in the prompt.

The agent loop should end with evidence, not confidence.

6. Permissions define the trust boundary

A harness must decide whether an action runs immediately or waits for review. Older systems often asked the user to approve each new operation, with an escape hatch that approved everything. Newer systems can use an autonomous reviewer to inspect actions and surface only those judged risky.

That convenience changes the shape of trust. Permission granularity can expand as a user gains confidence, but the harness still needs clear scopes, useful explanations, and a way to stop or revise an action.

The larger lever

Model size is only one way to scale AI output. The harness is another: it determines how long a model can work, what it can remember, how many workers it can coordinate, which tools it can use, and whether the result is verified. The source article points to striking gains in cost and benchmark performance from harnessed systems, and to foundation models increasingly being trained with these environments in mind.

The practical takeaway is simple: when evaluating an “agent,” inspect the software around the model. Its loop, context policy, memory, orchestration, tools, checks, and permissions may matter as much as the model underneath.
